# Модель деятельности профессии

Модуль строит для каждой профессии одну проверенную **модель деятельности**: функции → задачи → знания, умения,
инструменты → межпрофессиональные области знаний. По ней руководитель образовательной программы получает
рекомендации по составу программы, а методист — проверенные задачи для РПД.

**Решения принимает алгоритм, а не LLM.** LLM только извлекает утверждения из свободного текста, и у каждого
утверждения есть дословная цитата, которую проверяет код. Статусы, тренды, рекомендации и тексты объяснений
считаются по формулам; все пороги — в [`config/activity_model.yaml`](config/activity_model.yaml) с комментариями.

## Быстрый старт (локально)

```powershell
Copy-Item local_users.example.txt data\local_users.txt
.\.venv\Scripts\python.exe -m scripts.seed_activity_demo --reset
.\.venv\Scripts\python.exe -m streamlit run app.py
```

В `.env` нужны `APP_ENV=development` и `LOCAL_USERS_FILE=data/local_users.txt`. Учётные записи — в
`data/local_users.txt` (руководитель, методист, эксперт). Для генерации РПД нужен запущенный воркер
(задача VS Code «Воркер» или `python -m workers.course_worker`). **После обновления кода воркер нужно перезапустить.**

Демо-сид удаляет и пересоздаёт только записи с флагом `is_demo`. Все демо-экраны и экспорты помечены
«ДЕМО: синтетические данные».

## Роли и кабинеты

| Кабинет | Кто | Что делает |
| --- | --- | --- |
| `/head` | руководитель ОП (`program_head`) | профессии, источники, модель, эксперты и раунды Дельфи, программа и рекомендации, сигнал по профилю, карта знаний, очередь методиста, экспорт |
| `/teacher` | методист (`teacher`) | «Мои дисциплины в программах» (закреплённые задачи, РПД по модели), «Карта знаний» (идеи проектов), прежние курсы |
| `/expert` | эксперт-практик | анкета по карточкам (2 раунда), прежние интервью по курсам |

Вход: справочники Yandex `TEACHERS_INDEX_ID`, `EXPERTS_INDEX_ID` и новый `PROGRAM_HEADS_INDEX_ID` (тот же
формат файла). Для разработки — локальный файл `LOCAL_USERS_FILE` с полем «Роль» (только `APP_ENV=development`).

Каждая версия модели хранит полный JSON (`model_versions.content`), хэш правил и хэш входных данных. Если данные
и конфиг не менялись, новая версия не создаётся. Два прогона на одних данных дают побайтно одинаковый JSON
(проверено тестом).

### Связь с РПД (7.14)

Руководитель закрепляет дисциплину за методистом. Методист в «Мои дисциплины в программах» нажимает
«Создать РПД по модели деятельности»: в курс сохраняется снимок задач модели (статусы «Подтверждено» и
«Предварительно», покрытые дисциплиной). Граф генерации берёт задачи из снимка без вызова LLM, каждая задача
становится источником типа `ActivityModel` с «почему здесь» и цитатами, интервью по курсу не запрашивается,
`Topic.activity_task_ids` ссылается на задачи модели. Курсы без снимка генерируются как раньше и помечаются
«Модель деятельности не проверена экспертами».

## Сценарий демо (3 минуты)

1. Руководитель → «Профессии» → «Backend-разработчик»: функции, задачи, статусы, тренды, паспорт данных.
2. Раскрыть задачу: «Почему задача включена» — доля работодателей с ДИ, k/n экспертов с ДИ, ТФ ПС, цитаты.
   Кнопки «Рынок», «Эксперты», «Источники», «Приоритет» раскрывают формулу и исходные данные.
3. Вкладка «Исключённые эксперты»: 6 из 45, причины (в том числе «да» на «Проектирует систему капельного полива грядок»).
4. Вкладка «Спорные»: «Проверяет код, сгенерированный ИИ-ассистентами» — нужно ещё ≈ 10 экспертов;
   «Настраивает Kubernetes-кластеры» — спорно по существу, расслоение «малые компании 85 % / крупные 20 %».
   Подсказка «Почему 10 или 50 экспертов».
5. «Моя программа»: убрать 2 (PHP/SOAP, Java EE), объединить 2 (тестирование + контроль качества), обновить
   (базы данных, Python, проектирование), создать 2 (эксплуатация и наблюдаемость, анализ требований),
   фундамент сохранить. Баланс ЗЕТ, решения «принять / отклонить / отложить» с комментарием.
6. «Сигнал по профилю»: «Профиль трансформируется», A/B/C отдельно, роль-преемник «Платформенный инженер»
   с процентом сохранения программы.
7. Методист → «Карта знаний» → «Теория графов»: бэкенд (граф зависимостей), аналитик данных (графы связей),
   логистика (маршруты), платформенный инженер — реальные задачи как идеи проектов.

## Допущения

Там, где промт не задаёт решение, выбран самый простой прозрачный вариант.

1. **Формулировки ПС** хранятся дословно (отглагольные существительные: «Проектирование баз данных»).
   Правило «глагол в 3-м лице» применяется к вакансиям и свободному тексту. Ключ формулировки сопоставляет
   «Разработка …» и «Разрабатывает …» по основе глагола.
2. **Сопоставление формулировок** — точный ключ (основа глагола + понятия объекта с синонимами
   `config/analysis.yaml`). Эмбеддингов в этой версии нет: пороги `merge.auto/review` зарезервированы, похожие
   формулировки (Жаккар ≥ `grouping.duplicate_review`) идут в очередь методиста и не сливаются автоматически.
3. **Отнесение задачи к функции**: ТФ профстандарта; иначе ближайшая функция при сходстве ≥ `grouping.auto`;
   иначе «Прочее (требует разметки)» с подсказкой в очереди методиста.
4. **Методист курса** работает в кабинете `/teacher`. В старых локальных справочниках запись «Роль: методист» сохраняет доступ к `/head`. Для новых записей кабинета `/teacher` используйте «Роль: методист курса».
5. **«Одинаковые ответы»** — совпадение всей карточки (ответ, важность, прогноз), а не только вердикта:
   добросовестный эксперт часто отвечает «да» на реальные задачи.
6. **«Исчезает»** ставится, только если задача раньше была на рынке (`k_emp_prev > 0`); иначе снижение видно по
   прогнозу экспертов и метка — «снижается».
7. **Тренды по прогнозу экспертов** считаются при `n_forecast ≥ n_min`. Бонус приоритета для «автоматизируется» −1,
   для «неоднозначно» 0. Приоритет не ниже 1.
8. **Компонент C** сигнала по профилю = доля «вырастет» минус доля «снизится»; риск при `C ≤ c_risk`
   (в тексте промта знак описан наоборот, порог −0.3 соответствует этой формуле).
9. **Нормировка A** — по `professions.meta.market_totals` (общее число работодателей в выгрузке источника),
   если задано; иначе показывается «без нормировки».
10. **Голоса привязаны к версии пункта.** Предложенная экспертом формулировка попадает в очередь методиста; если её
    принять, пункт получает новую версию, голоса за прежнюю формулировку остаются при ней и в расчёт не входят.
11. **R3** оценивает долю неподтверждённого содержания по темам с равными весами.
12. **R2 «добавить темы»** рекомендуется дисциплине, которая покрывает больше всего задач функции; для дисциплин,
    которые R3 предлагает убрать, R2 не выдаётся. **R3**: уверенность высокая, только если все «плохие» задачи
    отклонены экспертами. **R4** освобождает `min(ЗЕТ) × сходство` (округление до 0.5).
13. **Сохранение программы при переходе на смежную роль**: задача считается сохранённой, если у роли есть похожая
    задача (Жаккар ≥ `adjacent.task_similarity`) или все её области знаний.
14. **Демоданные**: 45 экспертов, из них 6 недобросовестных (надёжных 39), поэтому «спорно по существу» — при 21 из
    39, а не при 45 голосах. Фрагмент ПС 06.001 — демонстрационный, перед реальной работой загрузите официальный текст.
    Номер пункта ФГОС ВО 3++ о профстандартах сверьте по своему стандарту.
15. **Контрольные карточки** не имеют цитат из источников, поэтому на них нет блока примеров. Это может подсказать
    внимательному эксперту, что карточка контрольная; правило дублей это компенсирует.
16. **Вход**: сессия хранится во вкладке браузера (как и раньше в проекте), после перезагрузки страницы нужен
    повторный вход.

## Чего нет в этой версии

- Эмбеддинги для слияния формулировок (P2): используется точный ключ и очередь методиста.
- Экспорт DOCX/PDF (P2): есть HTML, Markdown и JSON; HTML можно сохранить в PDF из браузера.
